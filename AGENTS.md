# AGENTS.md: superpowers-extensions

A marketplace of 22 skill plugins (24 skills) that extend the obra/superpowers suite. The skills are
markdown, loaded by Claude Code, Cursor, Codex, Gemini, Copilot CLI and OpenCode. The only code is
Node.js: repo guard scripts in `scripts/`, helper scripts inside some skills, and the session-start
hook. What ships is what the manifests point at: `plugins/`, `hooks/`, and the manifest files at the
repo root.

## Layout

- `plugins/<name>/skills/<skill>/SKILL.md` is the source of truth for a skill. A plugin may hold more
  than one skill, for example `architecture-scan` and `unattended`.
- Tests live next to the code they cover, as `plugins/*/skills/*/scripts/**/*.test.mjs`.
- `docs/superpowers/specs`, `docs/superpowers/plans` and `docs/plans` are point-in-time records, and
  `docs/superpowers/evals` holds eval fixtures. Do not reformat them.
- `plugins/ui-design-system/skills/ui-design-system/design-systems/` is vendored from
  VoltAgent/awesome-design-md and refreshed weekly by `refresh-design-systems.yml`. Do not edit it by
  hand or lint it. A system the refresh adds must be added to its `INDEX.md`, with the count line.
- `CHANGELOG.md` is generated by release-please. `GEMINI.md` is a hand-kept list of `@` imports, one
  per skill.
- `.github/upstream-superpowers.json` pins the obra/superpowers release the suite builds on. Bump it
  only in the PR that adapts the suite to a new release.

## Build and test

There is no build. Node.js 24 passes everything below here, CI uses Node 26. Run `npm ci` first.

```bash
# CI job markdown-lint (lint.yml)
npm run lint:md

# CI job check-registries (lint.yml). check:upstream clones obra/superpowers, so it needs network.
npm run check:registries
npm run check:conventions
npm run check:upstream

# CI job test (lint.yml): first installs the SVG rasteriser librsvg2-bin
npm test

# CI job commitlint (lint.yml), pull requests only
npx commitlint --from "$BASE_SHA" --to "$HEAD_SHA" --verbose
```

Fast inner loop, no CI job:

```bash
node --test plugins/retro/skills/retro/scripts/digest.test.mjs
npx commitlint --from origin/master --to HEAD --verbose
```

`npm test` takes about a minute. Tests that need a tool skip themselves when it is missing: ffmpeg,
Chromium via Playwright, `shellcheck`, git LFS and an SVG rasteriser. A run without them reports a
nonzero skip count and still exits 0, so a skip is not coverage. CI installs only the rasteriser.

## Conventions and gotchas

- New plugin: run `npm run check:registries`. It names every registry file the plugin must appear in.
- New commit scope: add it to the scope-enum in `commitlint.config.js` in the same commit. The commit-msg hook (installed by `npm install`) runs commitlint.
- Specs go in `docs/superpowers/specs/`, plans in `docs/superpowers/plans/`. Commit them as `docs(design)` and `docs(plan)`.
- Before pushing: `npm run lint:md && npm run check:registries && npm run check:conventions && npm test`. CI also runs `npm run check:upstream`.
- The commit-msg hook skips with a warning when `node_modules/.bin/commitlint` is missing.
  CI rejects a scope that is not in the scope-enum. An empty scope is only a warning.
- The version lives in many files, and release-please bumps all of them. Do not edit them by hand;
  `check:registries` fails when they disagree. They are `package.json`, `package-lock.json`,
  `.release-please-manifest.json`, `CHANGELOG.md`, `gemini-extension.json`,
  `.cursor-plugin/plugin.json`, `.codex-plugin/plugin.json`, and `.claude-plugin/marketplace.json`
  in 23 places: `$.version` and `$.plugins[i].version` for each of the 22 plugins. The per-plugin
  `plugins/<name>/.claude-plugin/plugin.json` files carry no version.
- The `extra-files` list in `release-please-config.json` is index-based: a plugin is only bumped when
  an entry for its index in `marketplace.json` exists. Append a new plugin to the end of `plugins[]`
  and add the next `$.plugins[n].version` entry. Inserting in the middle shifts the other plugins.
- `hooks/session-start` carries a hard-coded skill list and the count "Twenty-four skills". The plugin
  names are checked, the count wording is not, so update it by hand.
- `check:conventions` fails when a plugin outside `project-orchestration` hard-codes a commit message
  or tag in its prose. Delegate to the Commit & Release Protocol in the project-orchestration skill.
- Markdown must pass `markdownlint-cli2`. `docs/plans`, `CHANGELOG.md`, `GEMINI.md` and the vendored
  design systems are excluded, and so are files git ignores.
- Exception to the org CI rules: this is not a .NET repo. It calls no `ci-baseline` workflow and has no
  coverage gate or Codecov check. Its guards are the four `lint.yml` jobs above.

## Org rules

These rules hold in every public MarcelRoozekrans repo.

### Commits and releases

- Conventional Commits. release-please reads them on the default branch, and the changelog sections
  in `release-please-config.json` decide which types count. The standard: `feat`, `fix`, `perf`,
  `deps` and `revert` open or update the release PR; `docs`, `test`, `refactor`, `build`, `ci`,
  `chore` and `style` do not, unless the commit is breaking or has a `Release-As:` footer. The
  release happens when that PR merges. A breaking change needs `!` or a `BREAKING CHANGE:` footer.
- A commit body never contains nested parentheses. release-please cannot parse them and silently
  drops the whole commit from the changelog, while the workflow still reports success.
- After merging a commit that should release, check that it appears in the release-please PR.

### Branches and pull requests

- Every change goes through a branch and a pull request. Never push to the default branch directly.
- A PR body says what the diff does, and nothing the diff does not do.
- Fix review findings in the PR under review, including small ones. File an issue only for a finding
  that belongs to other code, needs a design decision, is its own piece of work, or waits on
  something external.

### CI

- The .NET repos call the shared workflows of `MarcelRoozekrans/ci-baseline`, pinned to `@v1`, never
  `@main`.
- Its coverage gate fails the build when line coverage drops below the floor of 80%, and Codecov
  fails a PR that lowers project coverage by more than 1 percentage point. New code comes with
  tests.
- A repo with a lower floor documents the reason and links the issue that raises it.
